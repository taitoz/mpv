# mpv portable config

Переносимая конфигурация mpv для Windows: качественное воспроизведение обычного и VR-видео с максимально возможным использованием аппаратного декодирования и GPU-обработки NVIDIA и AMD.

## Цель проекта

- Поддерживать максимально широкий набор форматов, кодеков, разрешений и типов видео.
- Задействовать возможности GPU для максимального качества с приемлемой плавностью и минимальной лишней нагрузкой на CPU.
- Обеспечить переносимость: mpv и весь конфиг находятся рядом, без обязательной глобальной установки.
- Для VR предоставлять чистое flat-превью для ручного подбора параметров реставрации.
- Развить воспроизводимый процесс: просмотр исходника → настройка фильтров и шейдеров → проверка результата → обработка и сохранение нового видео.

Это цели, а не гарантия аппаратной поддержки любого кодека на любой видеокарте. Доступные режимы зависят от модели GPU, драйвера, разрядности, цветовой субдискретизации и сборки mpv/FFmpeg. Если аппаратный декодер не поддерживает источник, потребуется программное декодирование.

```text

    ├── vr_rst.conf               Экспериментальный профиль реставрации
    ├── vr_vsr.conf               Экспериментальный профиль VSR
    ├── scripts/
    │   ├── vr-detect.lua          ffprobe и выбор VR-профиля
    │   └── vr-look.lua            Управление направлением взгляда
    ├── shaders/
    │   └── vr-flat.glsl           Шейдер перепроекции
```

Показаны основные файлы, а не полный список. `~~/` в настройках mpv указывает на каталог конфигурации.

## Требования и запуск

- mpv для Windows с `gpu-next` и поддержкой нужного аппаратного декодера.
- Актуальный совместимый драйвер NVIDIA или AMD.
- `ffprobe` в `PATH` для определения VR по метаданным.
- `ffmpeg` для исследования источников и будущего процесса экспорта.

Из каталога с mpv, в `cmd.exe`:

```cmd
mpv "X:\Path\To\Video.mp4"
```

В PowerShell путь к программе запускается через `&`; пути с символом `$` удобнее заключать в одинарные кавычки.

## Текущее состояние аппаратного воспроизведения

- Обычное видео: `vo=gpu-next`, `gpu-api=vulkan`, `hwdec=vulkan`.
- Автоматические профили качества выбирают масштабирование и дополнительные шейдеры для обычного видео.
- VR: `vo=gpu-next`, `gpu-api=d3d11`, `hwdec=d3d11va` и GPU-перепроекция.
- На текущем ПК проверено аппаратное воспроизведение на NVIDIA GeForce RTX 3070.
- Полная совместимость с AMD и выбор оптимального backend для разных GPU ещё требуют проверки.

Для VR не используется CPU-фильтр `v360` и не добавляется `hwdownload` ради перепроекции. Небольшая нагрузка на CPU при воспроизведении нормальна.

## VR: чистое превью для реставрации

Базовый режим VR должен показывать исходник без дополнительных реставрационных шейдеров, шумоподавления, повышения резкости и нейросетевого апскейла. Единственное необходимое преобразование — VR → flat, чтобы удобно оценивать изображение на обычном мониторе.

Технически сама перепроекция выполнена шейдером `shaders/vr-flat.glsl`. Поэтому «без шейдеров» в контексте flat-превью означает **без дополнительных шейдеров улучшения**, а не отключение перепроекции. Цветовое преобразование и обычное масштабирование рендерера также остаются необходимыми; это не побитовая копия исходника.

### Автоматический выбор

VR-автоопределение разрешено **только для файлов с расширением `.mp4`**, без учёта регистра. Остальные расширения воспроизводятся без автоматического включения VR и без вызова ffprobe.

При открытии локального MP4 скрипт:

1. Асинхронно вызывает ffprobe и ожидает результат перед началом воспроизведения.
2. Проверяет метаданные сферической проекции и стереораскладки.
3. Если поддерживаемых метаданных нет, использует маркеры в имени файла.
4. Если определить VR нельзя, выбирает обычное воспроизведение.

Таймаут ffprobe — 10 секунд. При ошибке или отсутствии ffprobe остаётся определение по имени. Сетевые входы не передаются ffprobe; для подходящих имён сохраняется запасной разбор названия.

Поддерживаются `Spherical Mapping`, `Stereo 3D`, а также теги `projection`/`vr_projection`, `stereo_mode`/`stereo_layout`, `vr_fov`/`id_fov`. Неподдерживаемые проекции, сферический crop и поворот не угадываются. Fisheye требует явно заданных 190°/200° и SBS. Разрешение само по себе не доказывает тип VR.

| Обозначение в имени | Интерпретация |
| --- | --- |
| `180_3dv`, `180_TB`, `180_OU` | VR180, глаза сверху/снизу |
| `360_OU`, `360_TB`, `360_3dv` | VR360, глаза сверху/снизу |
| `180_3dh`, `180_SBS`, `VR180_SBS_LR` | VR180, глаза рядом |
| `360_3dh`, `360_SBS` | VR360, глаза рядом |
| `fisheye200`, `mkx200` | Fisheye 200°, SBS |
| `fisheye`, `mkx` | Запасной вариант fisheye 190°, SBS |

По метаданным также поддерживаются 180°/360° mono. Выбирается первый глаз в раскладке; для SBS LR это левый, для TB — верхний.

В консоли отображается основание выбора:

```text
VR detection: 360-sbs (metadata)
VR detection: vr180 (filename; no usable VR metadata)
VR detection: none (non-MP4 input; VR disabled)
```

### Управление и скриншоты

| Действие | Управление |
| --- | --- |
| Поворот VR-камеры | Удерживать `Alt + ЛКМ` и двигать мышь |
| Вернуть взгляд в центр | `Ctrl + Backspace` |
| Полный экран | Двойной щелчок ЛКМ |
| Скриншот с GPU-перепроекцией | `Ctrl + S` (`screenshot window`) |
| Обычный скриншот до GPU-шейдеров | `s` / `Shift + S` |

VR-привязки включаются только при активном шейдере перепроекции. Для обычных видео сохраняются обычные привязки, включая `Alt + ЛКМ` для pan.

Скриншоты сохраняются в PNG в `~/Downloads`. WebP-кодировщик текущей сборки mpv не открывается; PNG проверен. Скриншот окна отражает выбранный ракурс и масштаб вывода, а не исходное разрешение полного VR-кадра.

## Рабочий процесс реставрации

1. Открыть VR-видео в чистом flat-превью.
2. Выбрать ракурс и проблемные фрагменты: шум, блоки, banding, недостаток деталей, ringing.
3. Вручную подобрать цветовые параметры, deband, шумоподавление, повышение резкости и апскейл.
4. Сравнить обработку с исходником, проверить несколько сцен и отсутствие артефактов.
5. Зафиксировать параметры в воспроизводимой команде или профиле.
6. Применить проверенную цепочку к полному видео и сохранить результат.

Нужно различать **flat-превью одного глаза** и **реставрацию исходного полного SBS/TB-кадра**. Экспорт flat-ракурса не сохраняет полный VR-источник и его стереоскопию.

### Пример ручного подбора, cmd.exe

Пример параметров пользователя; качество и скорость нужно оценивать на конкретном источнике. Автопрофили отключены, поэтому VR → flat здесь автоматически не включается. Это просмотр полного исходного кадра с явно заданной реставрационной цепочкой.

```cmd
set "SOURCE=X:\Path\To\Video.mp4"
mpv --load-auto-profiles=no "%SOURCE%" ^
  --brightness=0 --contrast=0 --saturation=-15 --gamma=0 --hue=-5 ^
  --scale=ewa_lanczos --scale-antiring=0.3 ^
  --cscale=ewa_lanczos --cscale-antiring=0.3 --dscale=mitchell ^
  --correct-downscaling=yes --linear-downscaling=no ^
  --deband=yes --deband-iterations=3 --deband-threshold=32 --deband-range=16 --deband-grain=16 ^
  --glsl-shaders-clr ^
  --glsl-shaders="~~/shaders/FSRCNNX/FSRCNNX_x2_16-0-4-1_enhance.glsl;~~/shaders/adaptive-sharpen.glsl" ^
  --video-sync=audio
```

Отключение `load-auto-profiles` отключает именно условные профили, но не пользовательские Lua-скрипты. Для ручной настройки flat-превью понадобится явно включить подходящий VR-профиль и включить `vr-flat.glsl` в нужном месте цепочки; очистка `glsl-shaders` удаляет и перепроекцию.

### Обратный захват и кодирование: рабочий сценарий пользователя

Пользователь проверил свою полную команду mpv → rawvideo/NUT → FFmpeg → NVENC и подтвердил, что эффект реставрации присутствует в итоговом видео. Это рабочая отправная точка проекта; не нужно отказываться от неё только ради более тяжёлых и медленных моделей. По опыту пользователя, Topaz и Real Video Enhancer слишком медленны для его задачи.

При этом вклад каждого конкретного GLSL-шейдера ещё не изолирован независимым A/B-тестом. Подтверждение видимого эффекта и доказательство экспорта всей цепочки — разные уровни проверки.

Схема транспорта и кодирования после подбора параметров:

```cmd
set "OUTPUT=X:\Path\To\Video-restored.mp4"
mpv --load-auto-profiles=no "%SOURCE%" --o=- --of=nut --ovc=rawvideo --oac=pcm_s16le | ffmpeg -n -init_hw_device cuda=cuda:0 -filter_hw_device cuda -i pipe:0 -i "%SOURCE%" -map 0:v -map 1:a? -vf "hwupload,scale_cuda=4800:2400" -c:v hevc_nvenc -rc constqp -qp 18 -b:v 0 -c:a copy "%OUTPUT%"
```

Здесь намеренно не повторена вся цепочка реставрации: это сокращённая схема транспорта и кодирования, а не полная команда пользователя. Для рабочего прогона нужны выбранные и проверенные параметры обработки. Используется `-n`, а не `-y`, чтобы не перезаписать существующий файл; вход и выход должны иметь разные пути.

Критические ограничения:

- Режим кодирования mpv `--o` не является захватом окна `gpu-next`. Нельзя считать, что `--glsl-shaders`, GPU-deband, GPU-масштабирование и экранная цветокоррекция автоматически попадут в выходной поток.
- Проверено экспериментально: `--glsl-shaders` и vo-настройки (`brightness`, `deband`, `scale`) через `--o` не экспортируются — rawvideo из pipe остаётся исходного размера и без обработки. Эффект в раннем тесте давал `scale_cuda` ffmpeg.
- **Рабочий путь экспорта GLSL-обработки:** `--vf=gpu` (offscreen-контекст vo_gpu как фильтр, тот же `--glsl-shaders` применяется). Его опции `w`/`h` задают размер выхода фильтра; `WHEN`-условия апскейлеров (FSRCNNX и др.) сравнивают исходник именно с этим размером. Подробности и проверенные пороги — в разделе «VR-предпросмотр и экспорт: проверенные детали» ниже.
- Ограничения `vf=gpu`: статус experimental, выход в RGB и конвертируется в YUV на CPU, OSD рендерится софтверно, при одновременном `--vo=gpu` фильтрация задваивается.
- CUDA/NVENC — путь NVIDIA. Для AMD нужен отдельный совместимый вариант обработки и аппаратного кодирования, например с AMF там, где он доступен.
- Пайп rawvideo через CPU не гарантирует zero-copy: возможны большие расходы на передачу кадров и последующий `hwupload`.
- `scale_cuda` поддерживает не все входные пиксельные форматы; преобразования нужно проверить отдельно.
- Размер 4800×2400 подходит выбранному примеру, но не универсален для TB, mono и других раскладок.
- Нужно проверить синхронизацию и длительность при копировании аудио из второго входа, а также сохранность HDR, цветовых и VR-метаданных.
- Бинарный pipe следует проверять в `cmd.exe` или подходящей современной оболочке; Windows PowerShell 5.1 не следует использовать для такого транспорта без отдельной проверки.

## Конечная цель: XBVR → DeoVR на Quest 2

Результат обработки — полноценное стереоскопическое VR-видео для библиотеки XBVR и воспроизведения в DeoVR на Meta Quest 2. Важно сохранить исходную проекцию, оба глаза, порядок глаз, частоту кадров и синхронизацию звука. Flat-ракурс нужен для настройки на ПК, а не как замена полного VR-файла.

Критерии успеха: заметное улучшение в шлеме, стабильное воспроизведение и достаточная скорость обработки библиотеки. Максимальное разрешение само по себе не является целью.

### Оценка выбранного подхода

- Компактный нейросетевой апскейл FSRCNNX и аппаратное кодирование — перспективный компромисс между качеством и скоростью. FSRCNNX не является универсальной моделью видеореставрации и не гарантирует восстановление утраченных деталей.
- Контролировать сглаживание текстур шумоподавлением, ореолы от резкости, усиление блоков, мерцание и нестабильность деталей в движении.
- Проверить необходимость каждого масштабирования: увеличение FSRCNNX, уменьшение и дополнительный scale_cuda могут быть полезны, но лишние проходы не гарантируют улучшения.
- Проверить обработку глаз с изоляцией их границ: фильтры не должны смешивать изображения SBS/TB.
- HEVC/NVENC — основной кандидат для NVIDIA; QP 18 — отправная точка, а не универсальный оптимум. Проверять размер, пиковый битрейт и совместимость конкретного разрешения/fps на Quest 2.
- Проверять прямое воспроизведение через XBVR/DeoVR без дополнительного перекодирования и пропускную способность сети.
- Окончательное решение принимать по движущемуся изображению в Quest 2, а не только по скриншотам на мониторе.

### Следующий эксперимент

Сравнить один и тот же короткий фрагмент в четырёх вариантах:

1. Исходник.
2. Только масштабирование и кодирование.
3. Те же параметры выхода с добавленным FSRCNNX.
4. Полная реставрационная цепочка.

Для вариантов 2–4 сохранить одинаковые разрешение, fps и настройки кодирования. Зафиксировать время обработки, скорость в fps, размер и битрейт, артефакты и субъективный результат в DeoVR. Это проверит вклад FSRCNNX в экспорт и пользу полной обработки. Затем подобрать несколько умеренных пресетов по типу исходника вместо одного агрессивного универсального.

Готовый скрипт прогона: `tools\vr-ab-test.bat` в отдельном репозитории [taitoz/vfx](https://github.com/taitoz/vfx) (только cmd.exe). Результат пользователя: эффект FSRCNNX на выходе 4800×2400 **отчётливо виден в Quest 2**; результаты полной цепочки ещё не оценены.

### VR-предпросмотр и экспорт: проверенные детали

Настройки предпросмотра находятся в `vr_profiles.conf`, `scripts/vr-detect.lua` и `shaders/vr-flat.glsl`: `vo=gpu-next`, `gpu-api=d3d11`, `hwdec=d3d11va`, GPU-репроекция без CPU-фильтра `v360`. Предпросмотр одного глаза не следует путать с экспортом полного стереокадра SBS/TB.

`vr-ab-test.bat [1|2|3] [секунды]` (в репозитории [taitoz/vfx](https://github.com/taitoz/vfx)) — переменные SRC/OUTDIR/OUTBASE/START/END/OUTW/OUTH/QP сверху; имя варианта в суффиксе файла. Вариант 1 — mpv `vf=gpu` с FSRCNNX + adaptive-sharpen сразу в итоговом размере → rawvideo/NUT pipe → FFmpeg: RGB→NV12 по BT.709 → HEVC NVENC с тегами bt709/tv; вариант 3 — NVIDIA VFX VideoSuperRes по глазам через `vr-vsr.py` без mpv-рендера и шейдеров. Все варианты имеют одно разрешение `OUTW×OUTH` (по умолчанию 4800×2400).

Проверенные особенности:
- FSRCNNX включается только при выходе **строго больше 1.4× исходника по обеим осям**. Для 3400×1700 при 4096×2048 вывод с FSRCNNX и без него побайтно совпадает; порог — от 4760×2380.
- SSimDownscaler работает только при уменьшении; в цепочке с апскейлом он неактивен и убран из варианта 3.
- Неявное `format=nv12` в FFmpeg переводит RGB по BT.601 без тегов (чистый зелёный: Y=145 вместо 173 по BT.709). Нужно явно задавать `scale=out_color_matrix=bt709:out_range=tv` и теги bt709/tv на выходе.
- Медленный прогон при ~30% GPU / 40–50% CPU — признак последовательного конвейера (рендер → копирование кадра в RAM → пайп → CPU-конвертация → загрузка в NVENC), а не тяжёлых шейдеров.
- В проверенной сборке offscreen-фильтр создаёт Vulkan-контекст даже с глобальным `--gpu-api=d3d11`; это не API обычного VR-предпросмотра.

Выбор разрешения для Quest 2: у Quest 2 около 20 пикселей на градус, а VR180 с 1700 px на глаз даёт ~9.4 px/°, поэтому выход в любом случае ниже разрешения панели. 1920 смысла не имеет: это не родное разрешение и не FSRCNNX, только лишний ресемплинг. 2048 — лишь небольшой lanczos-апскейл без FSRCNNX. Разумные варианты: **родные 1700** (без апскейла, быстрее и меньше битрейт) или **2400** (FSRCNNX активен). Плавность и битрейт по Wi-Fi проверять в шлеме.

## Репозиторий

Корень Git-репозитория — каталог `portable_config`, не каталог с mpv.exe. Исходные конфиги, Lua-скрипты, GLSL-шейдеры и документация предназначены для версионирования.

`.gitignore` исключает кэш, историю просмотров, позиции воспроизведения, логи, временные файлы, резервные копии, медиа, результаты обработки, исполняемые файлы и персональные шрифты NetflixSans/TX-02. Нужные ресурсы интерфейса uosc остаются в составе исходников. Игнорирование не удаляет локальные файлы.

Клонирование само по себе не устанавливает бинарные зависимости. `tools/bootstrap.ps1` скачивает mpv/FFmpeg и подходящий `scripts/uosc/bin/ziggy-windows.exe` отдельно от исходников. До публикации проверить лицензии сторонних скриптов, шейдеров и ресурсов; локальное наличие файла не означает право на его распространение. Личные пути в новых примерах заменять на нейтральные.

## Дальнейшее развитие

### Аппаратные backend и качество

- Проверить NVIDIA и AMD на разных кодеках, разрешениях, HDR и разрядностях.
- Определить надёжную стратегию выбора Vulkan / D3D11VA и fallback.
- Разделить чистое превью, интерактивную реставрацию и offline-обработку.
- Проверить экспорт именно обработанного изображения, а не только декодированного исходника.

### VSR

- Исследовать включение VSR при воспроизведении, требования к драйверам и совместимым GPU/backend.
- Проверить результат и ограничения на VR, HDR и разных разрешениях.
- Измерить качество, плавность и нагрузку; не смешивать VSR с базовым чистым VR-превью.

Что известно для экспорта:
- В mpv VSR доступен только через `--vf=d3d11vpp=scaling-mode=nvidia:scale=<k>`, которому нужен D3D11-контекст окна. В режиме кодирования `--o` фильтр не создаётся (`Creating filter 'd3d11vpp' failed`: без VO нет D3D11-устройства; проверено на mpv 0.41 с `d3d11va` и `d3d11va-copy`). Значит, через mpv драйверный VSR не экспортировать.
- Драйверный RTX VSR (D3D11 video processor) по документации NVIDIA принимает вход от 360p до 1440p, выход до 4K, и не сообщает, включился ли он. Исходник 3400×1700 и выход 4800×2400 выходят за эти пределы — даже на воспроизведении он, вероятно, не включится, без видимой ошибки.
- Офлайн-экспорт — **NVIDIA VFX SDK (Maxine) Video Super Resolution** через Python-пакет `nvidia-vfx` (`vr-vsr.py` в репозитории [taitoz/vfx](https://github.com/taitoz/vfx)): режимы VSR LOW/MEDIUM/HIGH/ULTRA, а также DENOISE/DEBLUR/HIGHBITRATE; вход/выход — RGB на GPU. Лицензия SDK проприетарная NVIDIA: устанавливается пользователем, в проект не входит. Установка окружения и команды запуска описаны в `docs/vr_sr.md` того репозитория.

`vr_vsr.conf` уже существует как экспериментальный файл, но не подключён в `mpv.conf` и не считается проверенной реализацией. `vr_rst.conf` также не подключён по умолчанию.

### Установщик / обновление

**Текущий статус: тестовый bootstrapper для быстрого развёртывания среды проверок, не финальный установщик продукта.** Реализован `tools/bootstrap.ps1` для **Windows x64, PowerShell 5.1+**. Не требует Git, WinGet, прав администратора, изменения системного PATH или регистрации ассоциаций. ARM64/x86 пока не поддерживаются.

**План финальной поставки:** установщик на базе Inno Setup или аналогичного инструмента, автоматически собираемый через GitHub Actions и публикуемый в GitHub Releases одним установочным `.exe`. Выбранная модель первого публичного релиза — наш конфиг и мастер проверки зависимостей **без включения чужих бинарников и без их автоматического скачивания**. Текущий скачивающий PowerShell-bootstrapper остаётся отдельным вспомогательным инструментом разработчика.

План поведения установщика:

- Искать mpv, ffmpeg и ffprobe в выбранной папке и PATH; позволять указать расположение вручную. Проверять запуск и возможности, а не только наличие файлов: версии, Lua и `gpu-next` у mpv, нужные возможности FFmpeg для экспорта.
- Если зависимость не найдена или не подходит, показывать ссылки на источники и инструкцию ручной установки, затем предлагать «Проверить снова». mpv обязателен; ffprobe нужен для определения VR по метаданным, ffmpeg — для обработки/экспорта. Отсутствие последних не должно блокировать установку для обычного воспроизведения; ограничения должны быть явно показаны.
- Устанавливать конфиг в `portable_config` рядом с выбранным `mpv.exe`, сохранять пользовательские изменения, предоставлять резервное копирование и откат. Изменение пользовательского PATH сделать явной опцией; системный PATH не менять.
- Отдельно определить ручную установку и обнаружение бинарного помощника uosc/ziggy; не включать его незаметно в пакет. Персональные шрифты не распространять.

План лицензирования состава релиза:

- Исключить компоненты с неподтверждённой лицензией, если проверка происхождения/разрешения не решит вопрос: `film-grain`, `evafast`, `reload`, `ytsub`, `cycle-commands`, `custom-scripts`. Для `custom-scripts` сначала выяснить авторство. Вместе с исключением убрать соответствующие подключения, настройки и клавиши; проверить, что оставшийся конфиг работает без них.
- Для распространяемых скриптов, шейдеров и ресурсов сохранить авторские уведомления, приложить необходимые тексты лицензий и актуализировать `THIRD_PARTY.md`. Отказ от упаковки mpv/FFmpeg упрощает поставку, но не отменяет лицензии самого конфига и его компонентов.

План CI/CD:

1. На pull request и push выполнять применимые автоматические проверки исходников, скриптов и конфигурации. Проверочные зависимости CI не включать в пользовательский установщик.
2. Формировать отдельный staging-каталог релиза по явному списку разрешённых компонентов, без локального кэша, истории, личных файлов и сторонних бинарников. Проверять комплектность, уведомления и отсутствие исключённых компонентов/ссылок на них.
3. По версионному тегу или ручному запуску собирать установочный `.exe` на Windows-runner с зафиксированными версиями инструментов и проверять установку/удаление в изолированной папке без изменения рабочего окружения.
4. После успешных проверок публиковать в GitHub Releases установочный `.exe`, SHA-256 и сведения о версии/коммите. Исходники установщика и workflow хранить в репозитории. Подпись Authenticode — отдельный будущий этап после выбора доступного сервиса/сертификата; сейчас подписанный релиз не обещается.
5. GPU-декодирование, GLSL, VR и экспорт проверять отдельно на реальных NVIDIA/AMD: обычный облачный CI эти проверки не заменяет.

**Это план, не реализованное поведение:** Inno Setup-проект и workflow ещё не созданы, компоненты с вопросами по лицензии пока не удалены. Команды ниже описывают текущий тестовый bootstrapper, который по-прежнему скачивает бинарные зависимости.

Сначала скачайте/клонируйте этот проект либо сохраните отдельно `tools/bootstrap.ps1` и проверьте его содержимое. Запуск из корня проекта в PowerShell:

```powershell
.\tools\bootstrap.ps1 -Destination 'D:\Players\mpv' -PlanOnly
.\tools\bootstrap.ps1 -Destination 'D:\Players\mpv'
```

`-Destination` — папка **с mpv.exe**, не `portable_config`. Если политика Windows запрещает запуск скриптов, не меняйте её глобально; после проверки скрипта и при разрешении вашей политики можно запустить отдельный процесс:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\bootstrap.ps1 -Destination 'D:\Players\mpv'
```

Установщик получает последний стабильный mpv MSVC x64 непосредственно из релизов `mpv-player/mpv`, статическую full-сборку FFmpeg из `GyanD/codexffmpeg` и `uosc.zip` версии, указанной в загруженном `scripts/uosc/main.lua`. SHA-256 каждого бинарного архива сверяется с `digest` GitHub API; отсутствие/несовпадение хеша останавливает установку. Это проверка относительно метаданных GitHub, не независимая цифровая подпись издателя.

Конфиг скачивается из `taitoz/mpv`: ссылка `-ConfigRef` (по умолчанию `HEAD`) сначала разрешается в полный commit SHA. Каждый устанавливаемый файл проверяется по Git blob SHA-1 из дерева этого коммита. Корневая обёртка GitHub ZIP не устанавливается. Берутся все файлы коммита, а не локальные незакоммиченные изменения; `.git`, игнорируемые личные шрифты, кэш и история не скачиваются. Проверка Git blobs подтверждает соответствие дереву GitHub, но не заменяет проверку подписи коммита.

```text
D:\Players\mpv\
├── mpv.exe                     и остальные файлы дистрибутива mpv
├── ffmpeg.exe / ffprobe.exe / ffplay.exe
├── launch.cmd                  PATH меняется только для дочернего процесса
├── licenses\                   документация и лицензии сборки FFmpeg
├── portable_config\            всё содержимое корня проекта
│   └── scripts\uosc\bin\ziggy-windows.exe
└── .bootstrap\                 версии, staging, резервные копии и журнал
```

После успешной установки/обновления папка `-Destination` автоматически добавляется в **пользовательский PATH**: команды `mpv`, `ffmpeg` и `ffprobe` становятся доступны из других папок. Системный PATH не меняется; существующие записи сохраняются, повторная установка не добавляет дубликат (учитываются регистр, кавычки, завершающий слеш и переменные окружения). Перезапустите терминал и приложение, из которого он открыт (IDE/Windows Terminal), чтобы они получили новое окружение. В уже открытом PowerShell можно выполнить `$env:Path += ';D:\Players\mpv'`. Если в PATH раньше есть другая версия программы, её приоритет сохраняется; проверьте `Get-Command mpv, ffmpeg, ffprobe -All`.

Для полностью portable-режима без изменения PATH используйте:

```powershell
.\tools\bootstrap.ps1 -Destination 'D:\Players\mpv' -NoPath
```

`-PlanOnly` не меняет PATH. `-NoPath` не удаляет ранее добавленную запись; откат файлов также не меняет PATH, чтобы не затронуть пользовательские настройки. Если откат отменяет первую установку, ненужную запись удалите вручную. Если записать пользовательский PATH не удалось, файлы остаются установленными, а скрипт выводит предупреждение.

Для запуска без обновления окружения используйте `D:\Players\mpv\launch.cmd "X:\Path\To\Video.mp4"`: так ffprobe доступен независимо от текущей рабочей папки и при `-NoPath`. `yt-dlp` автоматически не устанавливается; для сетевого видео установите его отдельно. Пользовательские шрифты не распространяются.

Перед установкой проверяются запуск mpv/FFmpeg/ffprobe, наличие `gpu-next`, работа Lua и разбор конфигурации без загрузки сторонних скриптов. Только в проверочных запусках отключаются Windows Media Controls (`--media-controls=no`), чтобы избежать наблюдавшегося зависания SMTC при завершении mpv; обычное воспроизведение это не меняет. При таймауте ошибка включает аргументы запуска и захваченный вывод. Проверка не подтверждает аппаратное декодирование, Vulkan/D3D11 на конкретном GPU, компиляцию всех GLSL, VR или экспорт: после установки выполните медиатест ниже. Не поддерживающая Lua/нужный рендерер сборка не заменит текущую установку.

**Обновление:** закройте mpv и процессы обработки, повторите команду с тем же `-Destination`. Неизменённые управляемые файлы заменяются с резервным копированием; пользовательские файлы не удаляются. Изменённые либо ранее неуправляемые конфиги сохраняются, а новые варианты попадают в `.bootstrap/backups/<id>/incoming/` с предупреждением. Такие конфликты нужно объединить вручную; записанные версии загрузок не означают, что конфликтующие файлы были заменены. Изменённые/неуправляемые бинарники вне `portable_config` блокируют замену: для первого запуска предпочтительна новая папка. Удалённые апстримом файлы пока сохраняются; устаревшие скрипты могут требовать ручного разбора. Автоматического слияния нет.

Версии, полные хеши архивов, вывод `--version` и хеши управляемых файлов записываются в `.bootstrap/installed.json`. Для повторного использования бинарных ZIP можно указать `-DownloadCache 'D:\Cache\mpv-bootstrap'`: каждый найденный архив всё равно проверяется по SHA-256; несовпадение блокирует установку, а не перезаписывает кеш. Конфиг скачивается заново и проверяется по дереву коммита. Для воспроизводимого запуска укажите версии явно:

```powershell
.\tools\bootstrap.ps1 -Destination 'D:\Players\mpv' -ConfigRef '<full-commit-sha>' -MpvVersion 'v0.41.0' -FFmpegVersion '9.0.2'
.\tools\bootstrap.ps1 -Destination 'D:\Players\mpv' -Rollback
```

`-Rollback` восстанавливает предыдущие файлы, а новые перемещает в резервную копию, не удаляя их. Позднейшие изменения управляемых файлов блокируют откат. При ошибке копирования запускается автоматическое восстановление. После прерывания процесса журнал `prepared` блокирует следующую установку; для восстановления укажите ID из сообщения/папки резервной копии:

```powershell
.\tools\bootstrap.ps1 -Destination 'D:\Players\mpv' -Rollback -BackupId '<id>'
```

Блокировка предотвращает одновременные установки. Файлы и журнал заменяются через временный файл и атомарное переименование; для обновлений рекомендуется NTFS с поддержкой `File.Replace`. Staging, временные файлы после аварий и резервные копии намеренно не очищаются автоматически и могут занимать много места. Установка не управляется WinGet: не используйте `winget upgrade` для этих же файлов. Перед публичным распространением остаётся необходим аудит компонентов `unverified` из `THIRD_PARTY.md`.

Офлайн-тесты (без загрузки/запуска бинарных зависимостей; тестовые папки остаются в `%TEMP%`):

```powershell
.\tools\bootstrap-tests.ps1
```

Дополнительная проверка уже скачанного mpv: 30 запусков Lua-пробы и разбор соседнего `portable_config`, без установки и загрузок:

```powershell
.\tools\bootstrap-tests.ps1 -MpvExecutable 'D:\Players\mpv\.bootstrap\staging\<id>\payload\mpv.exe'
```

## Проверка изменений

Короткая проверка воспроизведения без звука и автоплейлиста:

```cmd
mpv "X:\Path\To\Video.mp4" --frames=5 --no-audio --keep-open=no --autocreate-playlist=no --save-position-on-quit=no
```

Проверять сообщение VR detection, выбор профиля, строку аппаратного декодирования и отсутствие ошибок шейдера/фильтров. Для изменений автопрофилей дополнительно проверять переходы VR → VR другого типа → обычное видео. Короткий запуск не заменяет визуальную оценку и длительную проверку производительности.

Цели и технический контекст для следующих сессий сохранены в `AGENTS.md`.
